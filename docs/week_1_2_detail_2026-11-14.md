# 第一、二周详细计划（供审阅）

范围：2026-11-14 至 2026-11-27，衔接[四周执行计划](execution_plan_2026-11-14.md)。
状态：审阅草案。以下为任务、建议范围和验收证据，尚未开展相应实现与实验。
协作：工程、机制、实验三个负责人。日次表示推进顺序，不要求所有人每天整天工作；暂按每人每周约 12–18 小时估算，并预留缓冲。

## 1. 两周结束时应看到什么

第 1 周：从真实运行中拿出一个可追踪的问题，说明问题发生时各 Agent 正在执行什么、系统知道什么、哪些要求满足或未满足、哪些仍然未知。

第 2 周：对同一个问题，比较原有覆盖选择和新方法选择哪些计划，给出范围内候选改法、联合检查结果，并用执行或独立案例验证支持结论。

两周目标集中在 A（自主运行）、B（强自动修复）、D0/D1 的范围选择内核。完整人工审阅请求、预算扣减、人审联合提交和人工效果测量在第 3 周接入。

建议的两处范围调整：

1. 第一周完成最小计划适配与少量规则诊断，不要求全游戏约束建模。
2. 第二周先建立有限域枚举及独立验证参照；是否引入 SMT/CP-SAT 由实际变量规模决定。求解器名称不作为验收标准。

### D1：先做到“结果能对应到一次明确运行”

当前相关位置：run.py 的环境初始化、utils.py 的参数解析与统计。

拟新增或落实的内容：

- seed、experiment_id、repeat_id 和 condition；第一阶段只启用已实现条件，其他条件明确拒绝，避免标签不同却运行同一流程。
- 记录模型名、采样设置、提示摘要、代码实际内容摘要、依赖版本、Agent 数量及停止上限。
- 每次运行用独立目录保存 config、events、summary。
- 初始世界摘要与种子关联；地图复现与 LLM 输出复现分别描述。
- 同一初始配置的模型输出可以不同，不要求把完整轨迹强行做成确定性。

先用短运行验证记录和计量，再选择至少 1–2 局足以观察任务链进展的运行。初始上限可沿用 350；实际调用规模依据短运行成本确定。没有获得钻石也保留结束原因和阶段进展。

### D2：日志记录实际变化

当前相关位置：run.py 的主循环、utils.py 的动作处理、资源交换和统计。

最少事件：

- plan_proposed、plan_committed；
- action_attempt、environment_transition；
- item_transferred、milestone_reached；
- plan_completed / failed / replaced；
- episode_terminated，区分目标达成、超时、死亡和技术错误；
- model_usage 与耗时，区分聊天、Embedding 和重试。

记录环境步数与墙钟时间。原有 CSV 可以保留，新增事件流用于机制分析。

从日志检验：

1. 模型说“分享”但未实际转移物品，不能计作分享成功。
2. done 不能直接当成任务成功。
3. 物品数量/成就大于零的首次时刻应被记录，不依赖必须等于 1。
4. 同一事件可以找到之前的计划版本和执行结果。

### D3：计划接口只表达真实承诺

Plan 第一版只需：

agent_id、plan_id、version、当前目标、操作和参数、正在执行的技能、执行状态、允许编辑字段。

当前代码主要保留一个高层操作及执行状态。先可靠表示这个承诺和已知依赖，不把一句自然语言扩写成未经验证的完整未来技能序列。

Snapshot 至少包含：

- 所有相关 Agent 的已承诺计划，包括本步不重新调用 LLM 的 Agent。
- 在线可用事实、来源、观察时间及未知字段。
- 已知资源/参与承诺和当前局部问题。
- 本次允许改变的字段域。

事实来源规则：

- 自身观测和正式收到的信息进入在线快照。
- 全局工作台/熔炉广播须被明确列为公共信息，或按信息政策处理；各组一致。
- 其他 Agent 的私有库存或全图状态不能通过直接读取模拟器悄悄进入选择器。
- 离线评估真值单独保存。

交付一份短接口说明与可序列化样例，供三个负责人共用。

### D4：CUBE 探路控制投入

建议 CUBE 探路预算先限定为 8–12 人时，第三方依赖使用独立环境或隔离配置。

检查：

- 来源与版本可记录，能运行支持的最小场景。
- 初始配置能固定或保存；任务可解。
- 能区别一次有效推动与最终交付。
- 能识别当前合法参与、位置、方向和合作尝试。
- 哪些字段可编辑，是否真的存在时序/等待接口。
- 是否支持快照，或能通过固定初始状态与记录动作重建干预前缀。

接通后只跑最小任务，不立即迁移完整规划框架、做大规模实验或美化界面。

若未接通，列出具体阻塞项、预计额外工时及替代验证范围。若 MA-Crafter 不能提供足够的联合修改问题，CUBE 就关系到主创新的必要性，需要优先解决或收缩研究主张，不能仅作为报告中的名称保留。

### D5：先建少量可信的判断

建议优先规则：

- MA-Crafter：可观察的资源/工具前置条件、支持的分享操作及接收方、已知依赖。
- CUBE 接通后：合法参与、位置/方向与同一次合作尝试的兼容性。
- 没有支持证据的时序预测和未观察事实保留 unknown。

规则必须来自游戏本身。例如当前分享操作是否要求相邻，应按真实实现核对，不能新增距离限制。CUBE 没有的库存或截止时间也不进入编码。

两个层次分别记录：

- diagnosis：当前或预测要求是否 satisfied / violated / unknown。
- feasibility：授权字段中是否存在修改，结果为 SAT / UNSAT / UNKNOWN。

当前要求 violated 不等于不可修复；事实 unknown 也不等于违规。

共同合法性保护在所有条件中一致。合作预测的未知与物理动作的即时合法性分开处理。

### D6：案例库优先于样本数量

第一周争取得到 10–15 个去重案例，第二周视真实运行扩充到整体计划的 30–50 个目标。数量不足时报告实际情况。

每个案例包含：

- 原始 episode 与事件位置；
- 干预前可见事实和计划；
- 要解决的具体要求及局部时域；
- 编辑字段和容量；
- 已知可行改法、无法判断项或离线标注依据；
- 是否来自自然运行、受控游戏配置或合成约束测试。

至少覆盖：单改可修复、确需两计划联合修改、容量不足、局部检查漏掉的跨计划冲突、缺失证据，以及持续进展中的正常导航。

“有多个参与者”不直接推出“必须修改多个计划”；应检验只改其中一个能否完成修复。

### D8：自动修复基线具备实际能力

B 先用程序化或枚举/求解器给出的可执行改法，再进行有界定向重规划。修复轮数暂以 2 为起点，后续按预实验冻结。

同样记录 API 内部重试与真实调用数量；两轮修复不等于恰好两次 API 请求。

B 与后续人审组拥有同样在线信息、操作接口和自动修复机会。求解器已给出有效修改时，不专门留给人工。

结果至少区分：候选生成、验证通过、已提交、局部实际进展、缺陷恢复、最终任务完成。

### D9：D0 是需要认真实现的直接参照

按照报告的完整候选集合和覆盖目标实现 D0。先使用固定、可解释的权重和代价代理，避免第二周同时调整策略、权重和模型。

所有选择器使用相同输入接口：

Snapshot、Diagnosis、可编辑字段、容量上限，输出 ScopeResult。

风险排序和随机选择可以先做离线参照，不要求第二周就运行完整人审实验。

D0 也必须遵守权限边界与共同执行保护。不能故意只给 D0 不完整信息来制造 D1 优势。

### D10：生成可修改域

由要求关联到能够改变它的高层字段，确定实际允许的候选值，再形成候选范围。

初始只做少量、明确支持的修改，不要求生成任意长期计划。

4 Agent、编辑容量 2 时只有 11 个包含空集的范围，但范围内部仍可能有大量修改组合。分别记录范围数、字段组合数和检查时间，不能用“只有 11 组”推断整体搜索一定便宜。

设置候选数量/时间预算；预算不足时返回未完成搜索。只有穷尽声明的有限域且依据足够时，才在该域内报告无解。

### D11：联合检查是核心内容

共同检查选中计划和未选中承诺，覆盖所实现的参与、资源、依赖与时序关系。

检查须包含局部缺陷解决条件及保持有效工作的条件，“全部 noop”不能绕过研究问题。

输出：

- SAT：候选修改、改变字段、所用事实、版本和局部时域。
- UNSAT：仅针对声明的模型、权限域和时域，无解依据可核对。
- UNKNOWN：缺失事实、未支持规则、超时或搜索未完成，注明原因。

独立手工标注或另一套小规模枚举案例用于验证结果，避免用同一个检查器给自己提供全部“真值”。

### D12：从模型判断走到真实执行

对可重建的快照或干预前缀，重新核对状态和计划版本，再应用候选修改。执行后检查实际事件。

如果重放的状态摘要不匹配，标记为重放失败，不能当作同一个失败状态的因果比较。

第二周先完成同步自动修改的执行前校验和联合生效；完整人审请求、额度、超时与恢复事务在第三周完成。

共同保护覆盖动作处理中的即时副作用，包括 env.step 之前的资源交换。

### D13：比较“选得不同”与“修得更好”

同快照比较：

1. 风险排序；
2. 随机选择；
3. D0 原有覆盖；
4. D1 生成及联合检查。

必要消融：

- 相同候选池，仅做局部检查；
- 保留原有候选集合，增加联合检查；
- 使用生成候选与联合检查的完整版本。

这样尽量分开候选生成和检查带来的作用。如果无法分离，结论按模块整体增益表述。

记录潜在无效审阅机会、范围大小、实际恢复、耗时和调用消耗。第二周尚不能把潜在机会减少直接写成真实人工时间减少。

### D14：交付可演示证据

至少展示：

- 一个只需改一个计划的正确处理案例；
- 一个确实需要联合修改的案例；
- 一个范围不足、事实未知或检查预算不足的反例；
- 一次强自动修复成功的实际轨迹；
- 一个自动修复后仍未解决、可留给人审研究的问题，若确实存在；
- D0 / D1 的同快照结果和开销。

若自动修复已能解决所有目标问题，第三周优先验证这个结果与分布，不人为削弱 B。

## 5. 第二周验收包

- D0 和 D1 选择内核及相同输入接口。
- 范围内候选改法与 SAT / UNSAT / UNKNOWN 记录。
- 有独立依据的案例检查和小规模执行验证。
- 一份同快照对比及核心消融表。

## 6. 工作分配与依赖

| 角色 | 第 1 周重点 | 第 2 周重点 |
| --- | --- | --- |
| 工程 | seed、实际配置、事件日志、计划适配器 | 强 B 接线、同步执行前复核、候选改法执行 |
| 机制 | 规则、信息边界、字段域和案例预期 | D0、候选生成、联合检查与结果解释 |
| 实验 | CUBE 探路、自然快照、独立标注与成本计量 | 策略对照、受控反例、消融与第三周人审准备 |

推进依赖：

配置与日志 → Plan / Snapshot → 三值诊断 → B / D0 → 候选生成 → 联合检查 → 执行验证 → 对比及人审交接。

CUBE 探路与日志可以同时推进；约束编码须等待接口和规则核对。第二周机制工作较重，工程负责人接手接线，实验负责人负责独立案例，避免同一个人包办所有验证。

## 7. 建议优先审阅的四个取舍

| 取舍 | 建议值 | 改动后的影响 |
| --- | --- | --- |
| CUBE 在前两周投入多少？ | 第一周 8–12 人时探路，成功后只接最小场景 | 全量迁移会挤压核心机制；完全推迟可能失去联合修改的关键验证场景 |
| 第一版规划粒度多大？ | 当前已承诺高层技能与已知依赖 | 完整长时域技能序列会显著增加状态、时序和求解工作 |
| 求解器是否必须先上？ | 先有可核对的有限枚举参照，必要时换 SMT/CP-SAT | 上来依赖大型编码会推迟发现信息边界和规则本身的问题 |
| 每人每周能投入多少？ | 排期假设 12–18 小时 | 低于此投入时，应减少规则种类和环境迁移范围，保留强基线与关键验证 |

如果只调整一件事，优先确认 CUBE 的最小场景和本轮规则子集。它们直接决定核心机制是否有真实研究对象，以及两周工作能否收敛。
