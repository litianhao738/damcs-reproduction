## 范围选择参照

示例脚本比较：

1. `problem_owner_order`：按问题目标 Agent 排序分配容量。
2. `complete_related_groups`：在容量内覆盖完整关联 Agent 集合的结构参照。
3. `verified_scope`：从联合可修复见证中选择实际需改的字段范围。

前两种策略先决定范围，再用同一允许域中的见证评估范围内是否存在改法；该评估不反过来参与它们的选择。完整关联集合策略是本脚本明确给出的简化参照，未宣称完整复现中期报告的选择算法。

提供者单改案例中，按问题主体选择 Agent 0 的范围不可修复，完整关联集合 `[0, 1]` 超过容量 1；本方法找到 `[1]`。双提供者案例中，完整关联集合 `[0, 1, 2]` 超过容量 2，而 `[1, 2]` 已经足够。六 Agent 案例也展示了关联集合结构完整仍可能缺少联合可执行改法。

这些案例用于验证机制和解释范围差异，不能据此推断总体任务收益、人工时间节约或人类优于自动修复。

## 主循环与历史计划检查

两步主循环检查使用真实 Crafter 环境及受控的 AgentScope 回复：3 次初始规划、两个相关 Agent 各修复 2 轮，共 7 次本地规划回复。日志推荐编辑提供者，但当前步实际仍由提供者按原计划制造工具；被暂缓的制造者没有执行建议。该检查确认接线、两轮上限及建议与执行之间的边界，不是新增的 Qwen 接口实测。

本地记录：`results/scope_runner_smoke_20261115/summary.json` 与 `coordination.jsonl`。

另外，以相同种子重建初始 noop 后的环境，载入此前真实 Qwen 运行留下的计划。缺铁镐但钻石不在面前的 Navigator 依赖返回 `no_targets`，没有产生超出当前时域的可修复结论。该检查重建了观测，未使用当时归档的完整快照，仅用于确认支持边界。

## 当前结论范围

`repairable` 表示提交观测和显式有限域下，存在能产生列出目标事件并保持范围外已验证工作的联合见证。投影覆盖当前玩家动作阶段，分享先于环境动作；后续自主对象更新、生存结果和完整任务成功不在该见证的保证内。

输入缺失的影响按相关依赖传播。测试还覆盖共享目标先被他人采走、分享链执行顺序、建造先后顺序、未选计划的资源承诺和满能量睡眠者醒来后执行原操作等情况。

人工接口、候选实际提交和任务级效果实验尚待后续接入。枚举能直接解决的问题必须进入后续强自动基线，不能仅凭人工确认候选来主张人工增益。
