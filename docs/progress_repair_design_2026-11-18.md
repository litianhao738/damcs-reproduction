# 进度问题修复设计：新增条件 D，合并人审为 H

日期：2026-11-18。状态：**已实现**（同日），实际行为和验证结果见 [实现说明](implementation_2026-11-16.md) 第 4.1 节。实现时对本文做了几处修正，已在对应位置标出"实现修正"。

本文定了两件事：

1. A、B、C 保持原样，新增**进度问题**（计划合法但团队明显太慢）的处理，只在新条件 **D**（机器自动选方案）和人审条件 **H**（关键时刻由人选）中使用。
2. 原来的 H1 和 H2 合并为一个人审条件 **H**。H 使用原 H2 的审阅界面，并扩展到进度问题。原 H1 要回答的问题改用离线统计。

## 1. 为什么要改

现在的 C 和 H2 只修**不合法**的计划：东西不够、送的人手里没有、工具不对等。2026-11-18 跑的一局 H2 说明，在 Crafter 里这类问题大多不用 C/H2 出手，真正浪费时间的是**合法但慢**的计划。

这局的设置是 qwen3.8-max、关闭思考、6 个 Agent、150 步、种子 4，结果目录 `results/rerun_qwen38max_nothink_H2_6a_150s_20261118`：

- **大部分不合法计划由重规划解决。** 149 个规划步里，45 步出现不合法计划，其中 26 步由 B 的重规划改好。
- **剩下的 C/H2 修不了。** 剩下 19 步全是同一个问题：5 号想挖钻石，但全队没有铁镐，任何一步内的修改都修不好。
- **全局只叫了 0 次人。** 第 105、112 步"团队卡住"信号响了，但因为没有可修的方案而跳过（`no_new_review_scope`）。
- **第 29–72 步卡了 43 步，期间所有计划都合法，C/H2 根本不会去看。** 团队在第 29 步采到石头，第 72 步才做出石镐。这段时间负责做石镐的 0 号：
  - 第 29–44 步自己去砍树拿木头。同一时期其他人一共送给它 27 块石头，没人送木头，而石镐加熔炉总共只需要 5 块石头。
  - 第 45–70 步走回远处的旧工作台。LLM 多次插进相反方向的移动，打断了自动寻路，0 号来回走。
  - 5 号一直在睡觉，等铁镐好了再去挖钻石。

现有修复搜索在两处规则上管不到这种情况：

1. 它只把"缺材料"当作要修的问题（`build_repair_targets`），"工作台不在旁边"不算。
2. 它明确规定**不换目标**：0 号要做石镐，只能帮 0 号凑齐材料，不能改成由别人来做。

这只是一局的诊断，不能当作结果引用。但它说明：只修不合法计划，Crafter 里 C 和人审条件可能几乎没有事可做。

## 2. 条件设置

| 条件 | 内容 | 比前一个条件多了什么 |
| --- | --- | --- |
| A | DAMCS 底座 + 动作合法性检查 | 基线 |
| B | A + 最多 2 轮重规划 | LLM 自己改不合法的计划 |
| C | B + 自动修复不合法计划（可修复范围 S） | 验证过的最小修复。**与原定义相同，不改** |
| D | C + 进度问题：自动采用排第一的方案 | 处理"合法但慢" |
| H | D 的人审版：关键时刻由人决定，其余同 D | 人的判断 |

相邻两组只差一样东西：

- **B − A：** 重规划的作用。
- **C − B：** 可修复范围 S 的作用。
- **D − C：** 处理进度问题的作用。
- **H − D：** 人审的作用。

**为什么一定要有 D：** 如果只有人审条件能处理进度问题，那么它和 C 之间同时差了"多了进度方案"和"由人来选"两样，比 C 快时说不清是哪样起的作用。D 用同样的方案、由机器选，就把这两件事分开了。D 不需要真人，代码上就是总是采纳推荐方案的脚本审阅，不加等待。

**H 怎么处理两类问题：**

- **不合法问题：** 与原 H2 相同，开放可修复范围，在信号响时问人。
- **进度问题：** 在信号响时把候选方案列给人选。
- **两类问题都没问人时：** 和 D 一样自动处理。

所以 H 与 D 的差别只在关键时刻由谁来决定。

**A、B、C 中的进度问题：** 照常检测并记入日志，用于统计"进度问题数/局"，但不做任何处理，也不放进 B 的重规划反馈。所以 A、B、C 的行为和原来完全一样。

## 3. 合并 H1、H2，以及 H1 问题的替代

**原来的比较：** H1 开放出问题的 Agent，H2 开放可修复范围 S。两者比较，回答"开放能修好问题的人"是否优于"开放出问题的人"。

**合并的理由：**

1. **在 Crafter 里很可能看不出差别。** 重规划之后剩下的不合法问题很少，而且在上面那局里全都修不好，H1 和 H2 都没什么可审的。
2. **"只开放当事人"不适合进度问题。** 人审进度问题时是从列出的方案里选，原本就不是在"开放谁"这个层面上。
3. **省一半真人工作量。** 表 1 的真人审阅从 18 局降到 12 局。之后表 1 又去掉了 CUBE，只剩 Crafter 的 6 局。

**替代方法：离线统计。** 用实验中保存的问题快照（`failures/step_*.json`）比较两个比例：

- 只允许改当事人自己的计划时，能修好的问题占多少；
- 用可修复范围 S 时，能修好的问题占多少。

这项统计不调用模型，也不需要人，放在表 2。

实现修正：`scripts/evaluate_frozen_scopes.py` 原本就同时计算两种范围，输出中的 `strategies.owner` 是只改当事人，`strategies.verified` 是可修复范围 S，比较的字段是 `has_witness` 和 `target_coverage`，所以不需要新增选项。

**措辞限制：** 合并后，没有真人实验证明 S 是更好的**审阅界面**。论文里只能说 S 能修好的问题更多（离线统计），不能说"人用 S 审得更好"。

## 4. 进度问题的定义

| | 不合法问题（已有） | 进度问题（新增） |
| --- | --- | --- |
| 问的是什么 | 某个 Agent 这一步能不能做成 | 团队下一个里程碑是否来得明显太慢 |
| 修复对象 | 某个 Agent 的某个动作 | 团队的某个里程碑，谁完成都算 |
| 能否换人 | 不能 | 能（只限进度问题） |
| 验证方式 | 一步内精确验证 | 一步能达成的精确验证；需要走路的给估计步数，事后核对 |
| 在哪些条件中处理 | C、D、H | D、H |

### 里程碑和"下一个里程碑"

- Crafter 的里程碑就是指标里的 10 个阶段：采木、放工作台、木镐、采石、石镐、采煤、放熔炉、采铁、铁镐、采钻石。
- 每个里程碑的前提来自 `crafter/data.yaml`：
  - 石镐：1 木 + 1 石，在工作台旁；
  - 铁镐：1 木 + 1 煤 + 1 铁，在熔炉旁；
  - 工作台：2 木；
  - 熔炉：4 石；
  - 采石、采煤需要木镐，采铁需要石镐，采钻石需要铁镐。
- **下一个里程碑**是尚未达成、但前提里程碑都已达成的那些里程碑，可以同时有好几个。例如做出石镐后，采煤、放熔炉、采铁都是下一个里程碑。
- 团队进度改为数**主线里程碑**，所有条件的"团队卡住"信号都用这个口径。现在的计数包括全部成就，喝水、吃牛、睡醒也算进度，会把真正的卡住掩盖掉。

### 什么时候算进度问题

每个规划步，在不合法问题处理完之后（重规划和不合法修复都结束），对每个下一个里程碑 m 做检查：

1. **一步能达成，但当前计划没有做。** 存在某种改派，能让 m 在**这一步**达成，例如别人当步送来材料、由站在工作台旁的人来做；而当前计划这一步达不成 m，并且按估计还要至少 2 步。环境里"送东西"在其他动作之前执行，而且不看距离，所以这类改派可以用现有的联合模型精确验证。
2. **明显慢。** 按当前计划完成 m 的估计步数 E_now，比最好的候选方案 E_best 多出至少 Δ 步（`--slow_margin`，需要试跑调整）。实现修正：Δ 默认取步数上限的 3%，至少 2 步。350 步时为 10 步，与原设定相同；CUBE 30 步时为 2 步。
   - 当前计划怎么估：看哪些 Agent 的当前目标（模型回复里的 `goal.current_goal`）就是 m，取其中估计最快的。
   - 没有人在做 m 时，E_now 记为无穷大。也就是说，有人闲着、却没人去做下一个里程碑，也算进度问题。
3. **兜底：卡住但估不出来。** 主线里程碑连续一个卡住窗口（沿用 `--stall_fraction`）没有增加，又找不到可估计的方案，例如所需资源在地图上找不到，就记为状态"拿不准"的进度问题。实现修正：这类问题没有可选方案，所以只记录，不问人。

**冷却：** 某个里程碑提交过一次进度修复后，在这次分派结束（完成、失败或超出步数上限）之前，不再对它报进度问题。

## 5. 候选方案怎么生成

候选方案由固定模板生成，数量有限，每个都标明改了谁、估计多少步、是精确验证还是估计。

| 模板 | 内容 | 例子（第 46 步） | 验证 |
| --- | --- | --- | --- |
| 补给 | 有所缺物品的人，把物品远程送给要做的人 | 有木头的人送 1 块木头给 0 号 | 精确（一步） |
| 换人做 | 改由已经站在所需设施旁的人来做，缺的材料由别人当步送到；做出的工具之后可以转交 | 若 3 号站在工作台旁、手里有石头：0 号送木头，3 号当步做石镐 | 精确（一步） |
| 就地建 | 要做的人在当前位置放下所需设施，再做 | 0 号再砍 2 块木头，就地放工作台，然后做石镐 | 估计（多步） |
| 改派采集 | 把闲着的人派去采 m 所需的原料 | 5 号不再睡觉等待，去采煤或采铁 | 估计（多步） |
| 不改 | 保持当前计划 | 0 号走回旧工作台 | 作为对照 |

**闲着**的定义：

- 计划是 `noop` 或 `sleep`，而体力不低于阈值（体力低时睡觉是必要的）；
- 或者在送对方已经有富余的东西（超出下一个里程碑的用量）。

**选择顺序（实现修正）：** 原定"先改得少、再比步数"，但这样会让一个只改 1 人、要走 30 步的方案，排在改 2 人、只要 12 步的方案前面。实现改为：

1. 只考虑够格的方案，即第 4 节两条规则之一成立的方案；
2. 精确验证的方案优先；
3. 再比较代价：估计步数 + Δ × 改动人数，也就是每多改一个人，相当于多花 Δ 步；
4. 代价相同时，改动人数少的优先，再比估计步数。

不合法修复"先修得全，再改得少"的思路仍然保留，只是把"改动人数"换算成了步数来比较。

D 自动采用排第一的方案；H 把排序后的方案列给人。

**搜索规模：** 模板数 × Agent 数，6 个 Agent 时只有几十个候选，不需要现有的组合搜索。

**与不合法修复的关系：**

- 进度修复在不合法修复之后进行，所有候选都必须通过同一套合法性检查（`diagnose`）。
- 这一步已经被不合法修复改过的 Agent，不再参与进度修复。

## 6. 估计步数和执行

### 估计步数

- **地图：** 和 DAMCS 导航执行器用同一张地图。底座的 `Navigator` 本来就用整张语义地图寻路（`info['semantic']`），这是所有条件共用的设置。论文里要把"导航用整张地图"作为底座设置写明。
- **路径：** 用现有的 `PathFinding`，和执行器一致。
- **步数：** 估计步数 = 各 Agent 并行时最慢的那个人的（走路步数 + 采集、放置、制作的动作数）。送东西是当步、远程完成，不另计步数。
- **不考虑的因素：** 怪物、其他 Agent 挡路、昼夜、体力。所以只是估计，每次都要记下估计值和实际步数。这些因素也正是人审时人可以补充判断的地方。

### 执行

- **一步方案（补给、换人做）：** 和现在的 C 一样，作为当步计划修改提交，提交前复核。
- **多步方案（就地建、改派采集）：** 变成**锁定子任务**。
  - 被分派的 Agent 由现有的寻路执行器自动执行"走过去、采集或放置、制作"，期间不再每步问 LLM。
  - 锁定有步数上限：估计步数 × 1.5 + 3（向上取整，系数需要试跑调整）。
  - 以下任一情况发生就解除锁定：
    - 里程碑已达成（谁达成都算）；
    - 子任务完成；
    - 走不通；
    - 生命值低于阈值；
    - 超过步数上限。
  - 解除后在该 Agent 的上下文里写明结果，沿用现有的 `intervention_notes`，然后恢复 LLM 规划。
- **锁定与"送东西会打断"的规则：** 底座有一条规则，送东西给某人时，编号大于或等于对方的所有 Agent 都会被打断（`utils.py` 的 `_interrupt_agents_after_target`）。锁定中的 Agent 不受这条规则影响。这条规则本身属于 DAMCS 底座，所有条件共用，本设计不改。
- **存档：** 锁定状态属于人审控制器，会随 checkpoint 一起保存，中断后可以接着跑。

## 7. H 的审阅方式

问人的时机仍然用现有的三个信号，两类问题共用：

- **要做取舍：** 有多个改不同 Agent 的方案；
- **拿不准：** 只能兜底、估不出来。实现修正：进度问题在这种情况下没有可选方案，所以不问人，这个信号只对不合法问题起作用；
- **团队卡住。**

同一个问题 10 步内不重复问，不设次数上限。

**不合法问题：** 页面和原 H2 相同，开放可修复范围（最多 2 个 Agent）。

**进度问题：** 页面显示：

- 里程碑名称；
- 当前计划的估计步数；
- 候选方案列表，每个方案标明改了谁、改成什么、估计多少步、是精确验证还是估计；
- 排第一的方案默认选中。

人只能做三种操作：

| 操作 | 结果 |
| --- | --- |
| 从列表中选一个方案 | 采用所选方案 |
| 选"不改" | 保持当前计划 |
| 跳过 | 系统按排第一的方案自动处理，即与 D 相同 |

进度问题不允许自由修改，保证结果可以量化。

**判断标准：** 人的价值在于补上估计没考虑的信息，例如：

- 路上有怪物或岩浆；
- 某个 Agent 生命值很低；
- 原计划的 Agent 其实马上就要做成了；
- 被派走的 Agent 手里的工具马上要用。

具体标准写进 [审阅规程](review_protocol_2026-11-18.md)。

"要做取舍"在进度问题上会比较常见，所以每局问人的次数要按问题类型分开报告。

## 8. 新增指标

| 指标 | 含义 | 汇总字段（计划） |
| --- | --- | --- |
| 进度问题数/局 | 检查出进度问题的规划步数，按第 4 节的三种情况分开统计。所有条件都记录 | `progress_targets`、`progress_targets_<类型>` |
| 进度修复次数 | 提交的进度修复，按模板分开 | `progress_commits`、`progress_commits_<模板>` |
| 一步修复生效率 | 精确验证的方案在当步达成里程碑的比例 | `progress_exact_success` |
| 多步完成率 | 锁定期内完成子任务的比例 | `progress_commit_completed` / `progress_commits` |
| 估计误差 | 实际步数减估计步数，报告均值和中位数 | `progress_estimate_error` |
| 卡住总步数 | 主线里程碑超过卡住窗口没有增加的步数之和 | `stall_steps_total` |
| 锁定步数 | 锁定执行、没有调用 LLM 的 Agent 步数 | `committed_agent_steps` |
| 人审次数（按问题类型） | 不合法问题、进度问题各自问人的次数 | `requests_legal`、`requests_progress` |
| 人审选择 | 进度问题中人选了推荐方案、其他方案、"不改"、跳过的次数 | `progress_reply_<选择>` |

已有指标（钻石步数、阶段步数、修复生效率、花费等）不变。

## 10. CUBE 上的对应

2026-11-18 课题组决定三张表都不跑 CUBE。下面的实现保留，可用于附录；论文中不声称机制在另一个环境中同样有效。

- **里程碑：** 箱子送达，团队得分增加。
- **下一个里程碑：** 尚未送达的箱子。瓶颈通常是推面上还差几个人。
- **模板：**
  - "派 Agent i 去箱子 b 的推面"：多步，按到推面的最短路径估计；
  - "人齐了当步推"：一步，用现有联合模型精确验证。
- 2026-11-16 的 CUBE 诊断发现，时间主要花在最后一个人就位上（第一个人到达后还要 10–17 步）。这正是 CUBE 上的进度问题。
- 实现修正：
  - 前方被另一个箱子挡住的箱子不出方案，先处理挡在前面的那个。锁定任务执行中如果箱子被挡住，就解除锁定。
  - 只考虑向右推。两个箱子互相挡住时，必须先往别的方向推，当前设计给不出方案。

## 11. 局限与风险

- **估计不准：** 估计没考虑怪物和挡路，修完反而可能更慢。估计误差和"修复后是否真的更快"都要如实报告。D − C 为负时也要如实写出。
- **调参不能用测试种子：** Δ 和锁定系数需要调整，只在表格以外的种子上调（例如 7、8），不在 4、5、6 上调。
- **LLM 可能改回去：** 被改派的 Agent 解除锁定后，LLM 可能回到原来的目标。用多步完成率和解除后的行为来检查。
- **问人可能过多：** 进度问题出现得可能比不合法问题频繁，H 问人的次数可能明显增加，需要报告，必要时加大冷却时间。
- **没有真人对比审阅界面：** 合并 H1、H2 后，审阅界面的好坏只有离线证据（见第 3 节）。
- **证据还很少：** 本设计只基于一局诊断，在表 1–3 跑完之前，不能声称进度修复有效。
- **D 本身就是一个规划器（实现后发现）：** 离线端到端检查中，所有 Agent 的 LLM 回复一律是 noop，D 仍在第 100 步采到钻石（种子 4，6 个 Agent，150 步），C 一个里程碑都没完成。
  - 这说明进度修复本身就是一个基于合成配方和整张地图的规划器。D − C 里会包含这个规划器自身的作用，不只是"修复 LLM 的计划"。
  - 论文中需要用对照把这部分分开。建议：
    - 加一组"D，LLM 关闭"（零花费），给出"只靠机制"能达到的水平；
    - 报告锁定步数占全部 Agent 步数的比例（`committed_agent_steps`）。
  - 这一组是否加入表格，待课题组决定。
- **H 问人次数（实现后发现）：** 同一检查中，H 在每个进度问题上都因为 `choice` 而问人（10 次问了 10 次）。真人实验前应确认这个频率可以接受，必要时加大冷却时间，或只在 `stalled` 时问。
