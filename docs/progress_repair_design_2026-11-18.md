# 进度问题修复设计：让 C/H2 也修"合法但慢"的计划

日期：2026-11-18。状态：**设计稿，尚未实现**。实现完成并通过测试之前，表 1–3 不开跑（见 [实验表设计](experiment_tables_2026-11-17.md) 开头的说明）。

## 1. 为什么要改

现在的 C 和 H2 只修**不合法**的计划：东西不够、送的人手里没有、工具不对等。2026-11-18 跑的一局 H2 说明，在 Crafter 里这类问题大多不用 C/H2 出手，真正浪费时间的是**合法但慢**的计划。

这局的设置是 qwen3.8-max、关闭思考、6 个 Agent、150 步、种子 4，结果目录 `results/rerun_qwen38max_nothink_H2_6a_150s_20261118`：

- **大部分不合法计划由重规划解决。** 149 个规划步里，45 步出现不合法计划，其中 26 步由 B 的重规划改好。
- **剩下的 C/H2 修不了。** 剩下 19 步全是同一个问题：5 号想挖钻石，但全队没有铁镐，任何一步内的修改都修不好。
- **全局只叫了 0 次人。** 第 105、112 步"团队卡住"信号响了，但因为没有可修的方案而跳过（`no_new_review_scope`）。
- **第 29–72 步卡了 43 步，期间所有计划都合法，C/H2 根本不会去看。** 团队在第 29 步采到石头，第 72 步才做出石镐。这段时间负责做石镐的 0 号：
  - 第 29–44 步自己去砍树拿木头。同一时期其他人一共送给它 27 块石头，没人送木头，而石镐加熔炉总共只需要 5 块石头。
  - 第 45–70 步走回远处的旧工作台。LLM 多次插进相反方向的移动，打断了自动寻路，0 号来回走。
  - 5 号一直在睡觉，等铁镐好了再去挖钻石。

现有修复搜索在两处规则上管不到这种情况：

1. 它只把"缺材料"当作要修的问题（`build_repair_targets`），"工作台不在旁边"不算。
2. 它明确规定**不换目标**：0 号要做石镐，只能帮 0 号凑齐材料，不能改成由别人来做。

这只是一局的诊断，不能当作结果引用。但它说明：不扩展问题的定义，Crafter 里 C 和 H2 可能几乎没有事可做，表 1 中 C − B、H2 − C 会接近 0。

## 2. 核心改动：多一类问题，叫"进度问题"

| | 不合法问题（已有） | 进度问题（新增） |
| --- | --- | --- |
| 问的是什么 | 某个 Agent 这一步能不能做成 | 团队下一个里程碑是否来得明显太慢 |
| 修复对象 | 某个 Agent 的某个动作 | 团队的某个里程碑，谁完成都算 |
| 能否换人 | 不能 | 能（只限进度问题） |
| 验证方式 | 一步内精确验证 | 一步能达成的精确验证；需要走路的给估计步数，事后核对 |

五个条件之间的区别**不变**：仍然只在"谁来修"。两类问题在每个条件里都存在，处理方式见第 7 节。

## 3. 里程碑和"下一个里程碑"

- Crafter 的里程碑就是指标里的 10 个阶段：采木、放工作台、木镐、采石、石镐、采煤、放熔炉、采铁、铁镐、采钻石。
- 每个里程碑的前提来自 `crafter/data.yaml`：
  - 石镐：1 木 + 1 石，在工作台旁；
  - 铁镐：1 木 + 1 煤 + 1 铁，在熔炉旁；
  - 工作台：2 木；
  - 熔炉：4 石；
  - 采石、采煤需要木镐，采铁需要石镐，采钻石需要铁镐。
- **下一个里程碑**是尚未达成、但前提里程碑都已达成的那些里程碑，可以同时有好几个。例如做出石镐后，采煤、放熔炉、采铁都是下一个里程碑。
- 团队进度改为数**主线里程碑**。现在的"团队卡住"信号数的是全部成就，喝水、吃牛、睡醒也算进度，会把真正的卡住掩盖掉。

## 4. 什么时候算进度问题

每个规划步，在不合法问题处理完之后（重规划和不合法修复都结束），对每个下一个里程碑 m 做检查：

1. **一步能达成，但当前计划没有做。** 存在某种改派，能让 m 在**这一步**达成，例如别人当步送来材料、由站在工作台旁的人来做；而当前计划这一步达不成 m，并且按估计还要至少 2 步。环境里"送东西"在其他动作之前执行，而且不看距离，所以这类改派可以用现有的联合模型精确验证。
2. **明显慢。** 按当前计划完成 m 的估计步数 E_now，比最好的候选方案 E_best 多出至少 Δ 步（`--slow_margin`，默认 10，需要试跑调整）。
   - 当前计划怎么估：看哪些 Agent 的当前目标（模型回复里的 `goal.current_goal`）就是 m，取其中估计最快的。
   - 没有人在做 m 时，E_now 记为无穷大。也就是说，有人闲着、却没人去做下一个里程碑，也算进度问题。
3. **兜底：卡住但估不出来。** 主线里程碑连续一个卡住窗口（沿用 `--stall_fraction`）没有增加，又找不到可估计的方案，例如所需资源在地图上找不到，就记为状态"拿不准"的进度问题。

**冷却：** 某个里程碑提交过一次进度修复后，在这次分派结束（完成、失败或超出步数上限）之前，不再对它报进度问题。

## 5. 候选方案怎么生成

候选方案由固定模板生成，数量有限，每个都标明改了谁、估计多少步、是精确验证还是估计。

| 模板 | 内容 | 例子（第 46 步） | 验证 |
| --- | --- | --- | --- |
| 补给 | 有所缺物品的人，把物品远程送给要做的人 | 有木头的人送 1 块木头给 0 号 | 精确（一步） |
| 换人做 | 改由已经站在所需设施旁的人来做，缺的材料由别人当步送到；做出的工具之后可以转交 | 若 3 号站在工作台旁、手里有石头：0 号送木头，3 号当步做石镐 | 精确（一步） |
| 就地建 | 要做的人在当前位置放下所需设施，再做 | 0 号再砍 2 块木头，就地放工作台，然后做石镐 | 估计（多步） |
| 改派采集 | 把闲着的人派去采 m 所需的原料 | 5 号不再睡觉等待，去采煤或采铁 | 估计（多步） |
| 不改 | 保持当前计划 | 0 号走回旧工作台 | 作为对照 |

**闲着**的定义：

- 计划是 `noop` 或 `sleep`，而体力不低于阈值（体力低时睡觉是必要的）；
- 或者在送对方已经有富余的东西（超出下一个里程碑的用量）。

**选择顺序**沿用现在的规则，最后加一条步数比较：

1. 先修得全，即修好的问题多的优先；
2. 再改得少，即改动的 Agent 少的优先；
3. 最后比较估计步数，少的优先；
4. 精确验证的方案优先于只有估计的方案。

**搜索规模：** 模板数 × Agent 数，6 个 Agent 时只有几十个候选，不需要现有的组合搜索。

**与不合法修复的关系：**

- 进度修复在不合法修复之后进行，所有候选都必须通过同一套合法性检查（`diagnose`）。
- 这一步已经被不合法修复改过的 Agent，不再参与进度修复。

## 6. 估计步数和执行

### 估计步数

- **地图：** 和 DAMCS 导航执行器用同一张地图。底座的 `Navigator` 本来就用整张语义地图寻路（`info['semantic']`），这是所有条件共用的设置。B 收到的反馈里会包含同样的距离信息，所以 B 和 C 掌握的信息相同，区别只在由谁来决定。论文里要把"导航用整张地图"作为底座设置写明。
- **路径：** 用现有的 `PathFinding`，和执行器一致。
- **步数：** 估计步数 = 各 Agent 并行时最慢的那个人的（走路步数 + 采集、放置、制作的动作数）。送东西是当步、远程完成，不另计步数。
- **不考虑的因素：** 怪物、其他 Agent 挡路、昼夜、体力。所以只是估计，每次都要记下估计值和实际步数。

### 执行

- **一步方案（补给、换人做）：** 和现在的 C 一样，作为当步计划修改提交，提交前复核。
- **多步方案（就地建、改派采集）：** 变成**锁定子任务**。
  - 被分派的 Agent 由现有的寻路执行器自动执行"走过去、采集或放置、制作"，期间不再每步问 LLM。
  - 锁定有步数上限：估计步数 × 1.5 + 3（向上取整，系数需要试跑调整）。
  - 以下任一情况发生就解除锁定：
    - 里程碑已达成（谁达成都算）；
    - 子任务完成；
    - 走不通；
    - 生命值低于阈值；
    - 超过步数上限。
  - 解除后在该 Agent 的上下文里写明结果，沿用现有的 `intervention_notes`，然后恢复 LLM 规划。
- **锁定与"送东西会打断"的规则：** 底座有一条规则，送东西给某人时，编号大于或等于对方的所有 Agent 都会被打断（`utils.py` 的 `_interrupt_agents_after_target`）。锁定中的 Agent 不受这条规则影响。这条规则本身属于 DAMCS 底座，是否对所有条件修改另行决定，本设计不改。
- **存档：** 锁定状态属于人审控制器，会随 checkpoint 一起保存，中断后可以接着跑。

## 7. 五个条件怎么处理进度问题

| 条件 | 不合法问题（不变） | 进度问题（新增） |
| --- | --- | --- |
| A | 拦下并记录 | 只记录，不处理 |
| B | 把问题反馈给 LLM，重规划最多 2 轮 | 把进度问题和相关事实（里程碑、当前估计步数、各人持有的物品、各人到所需设施或资源的距离）放进同一次重规划反馈，不给出候选方案，由 LLM 自己改 |
| C | 自动套用验证过的最小修复 | 自动套用排第一的候选方案 |
| H1 | 开放出问题的 Agent | 开放这个里程碑的当事人：当前目标是 m 的 Agent；没有人在做时，开放估计最快的那个 Agent。只能改他自己的计划 |
| H2 | 开放可修复范围 | 开放排第一的方案和其他候选方案涉及的 Agent（最多 2 个），把模板方案列出来让人选，"不改"始终是一个选项 |

人审页面上，进度问题只能**从列出的方案里选**，或者选"不改"，不允许自由修改，保证结果可以量化。每个方案都显示改了谁、估计多少步、是精确验证还是估计。

问人的时机仍然用现有的三个信号：

- **要做取舍：** 有多个改不同 Agent 的方案；
- **拿不准：** 只能兜底、估不出来；
- **团队卡住。**

"要做取舍"在进度问题上会比较常见，所以每局问人的次数要按问题类型分开报告。

## 8. 新增指标

| 指标 | 含义 | 汇总字段（计划） |
| --- | --- | --- |
| 进度问题数/局 | 检查出进度问题的规划步数，按第 4 节的三种情况分开统计 | `progress_targets`、`progress_targets_<类型>` |
| 进度修复次数 | 提交的进度修复，按模板分开 | `progress_commits`、`progress_commits_<模板>` |
| 一步修复生效率 | 精确验证的方案在当步达成里程碑的比例 | `progress_exact_success` |
| 多步完成率 | 锁定期内完成子任务的比例 | `progress_commit_completed` / `progress_commits` |
| 估计误差 | 实际步数减估计步数，报告均值和中位数 | `progress_estimate_error` |
| 卡住总步数 | 主线里程碑超过卡住窗口没有增加的步数之和 | `stall_steps_total` |
| 锁定步数 | 锁定执行、没有调用 LLM 的 Agent 步数 | `committed_agent_steps` |
| 人审次数（按问题类型） | 不合法问题、进度问题各自问人的次数 | `requests_legal`、`requests_progress` |

已有指标（钻石步数、阶段步数、修复生效率、花费等）不变。

## 9. 对三张表的影响

- **表 1：** 结构不变。C、H1、H2 的含义扩展为"两类问题都修"，A 和 B 也会检查出进度问题（A 只记录，B 放进反馈）。主要比较的读法不变：C − B 仍是"同样的诊断下，验证过的修复是否胜过 LLM 自己改"，H2 − C 仍是人审的增量。
- **表 2：** 在"自动"部分加两行，在线版本从 7 个变为 9 个，共 54 局（3 个种子 × 2 次重复）：

  | 组 | 版本 | 去掉或替换了什么 | 对应指标 | 运行名（计划） |
  | --- | --- | --- | --- | --- |
  | 自动 | − 进度问题 | 只修不合法问题，即现在的 C | 卡住总步数、钻石步数 | `C-legal-only` |
  | 自动 | − 锁定执行 | 多步方案只写进上下文提示，不锁定 | 多步完成率、估计误差 | `C-no-commit` |

- **表 3：** 结构不变。
- **CUBE：** 表 1 里 CUBE 也要跑 B、C、H2，所以 CUBE 适配器也要实现进度问题，否则两个环境的 C/H2 含义不一致。见第 10 节。

## 10. CUBE 上的对应

- **里程碑：** 箱子送达，团队得分增加。
- **下一个里程碑：** 尚未送达的箱子。瓶颈通常是推面上还差几个人。
- **模板：**
  - "派 Agent i 去箱子 b 的推面"：多步，按到推面的最短路径估计；
  - "人齐了当步推"：一步，用现有联合模型精确验证。
- 2026-11-16 的 CUBE 诊断发现，时间主要花在最后一个人就位上（第一个人到达后还要 10–17 步）。这正是 CUBE 上的进度问题。

## 11. 局限与风险

- **估计不准：** 估计没考虑怪物和挡路，修完反而可能更慢。估计误差和"修复后是否真的更快"都要如实报告。
- **调参不能用测试种子：** Δ 和锁定系数需要调整，只在表格以外的种子上调（例如 7、8），不在 4、5、6 上调。
- **LLM 可能改回去：** 被改派的 Agent 解除锁定后，LLM 可能回到原来的目标。用多步完成率和解除后的行为来检查。
- **问人可能过多：** 进度问题出现得可能比不合法问题频繁，H2 问人的次数可能明显增加，需要报告，必要时加大冷却时间。
- **证据还很少：** 本设计只基于一局诊断，在表 1–3 跑完之前，不能声称进度修复有效。

## 12. 实现步骤

1. **适配器接口：** 新增"主线里程碑""下一个里程碑""候选方案及估计步数"三个方法，Crafter、CUBE 各实现一份。主线里程碑进度替换"团队卡住"使用的成就计数。
2. **修复搜索：** 新增进度问题的问题类型和模板候选；一步方案复用现有联合模型做精确验证。
3. **人审控制器：** 处理进度问题；锁定子任务的分派、执行、解除和存档；信号和冷却；按问题类型计数。
4. **B 的反馈：** 重规划反馈里加入进度问题和相关事实。
5. **审阅页面：** 进度问题显示为方案列表加"不改"。
6. **汇总：** `run_experiments.py` 导出第 8 节的字段，新增 `C-legal-only`、`C-no-commit` 两个消融版本。
7. **离线测试：**
   - 用构造的状态复现第 46 步：0 号有木头、离工作台远，3 号在工作台旁、有石头。期望找到"换人做"，并通过精确验证。
   - 锁定的解除条件逐条测试。
   - 估计步数的计算。
   - 存档后恢复，锁定状态保持不变。
   - 不合法修复和进度修复在同一步的先后顺序。
8. **小规模试跑：** 在种子 7、8 上各跑 150 步的 C 和 `C-legal-only`，用来调 Δ 和锁定系数，并检查问人频率。只作为调参记录，不进表格。
