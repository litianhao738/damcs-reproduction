# 生成并选择可修复范围：实现计划

日期：2026-11-15。状态：核心范围生成、联合验证、选择及建议日志已实现。人工提交与任务级效果实验留待后续。

目标：在现有约束诊断和最多两轮定向重规划之后，从剩余问题中生成候选编辑范围，验证范围内存在何种修复，再选择一个范围及其依据。

本计划承接已确认的策略：在线检查使用各 Agent 已有观测和库存；自动修复采用最多两轮定向重规划；当前步仍不可执行的操作暂缓，正常导航继续。

## 1. 第一版范围与建议默认值

| 项目 | 建议 |
| --- | --- |
| 接入环境 | 当前 MA-Crafter |
| 验证时域 | 下一次环境步，包括该步之前的分享 |
| 编辑容量 K | 最多修改 2 个 AI Agent 的计划 |
| 输出数量 | 每个快照推荐 1 个联合范围，也可返回无推荐 |
| 首批问题 | 制造材料不足；目标材料已在面前时的采集工具不足 |
| 修改字段 | `operation`、`material`、`item`、`recipient`，按问题列出有限允许值 |
| 执行方式 | 先记录候选与选择结果，现有执行策略继续运行 |

当前默认 K=2、一步时域及表中的首批规则已接入代码。K 是编辑容量，与已确认的“两轮自动重规划”分别设置，可通过 `--scope_max_agents 1` 做容量对照，通过 `--scope_mode off` 关闭范围搜索。

现有 Plan 表示当前高层操作及参数。第一版以这些真实字段为基础；远距离导航、多步造工具链、设施建设与放置修复留待扩展。已有诊断可继续记录这些问题，本模块只对已覆盖的修改域和时域给出结论。

## 2. 范围的含义

- **编辑范围 S**：允许修改哪些 Agent 的哪些字段。
- **证据范围 E**：判断修复是否成立需要阅读哪些观测、库存和计划。E 可以包含 S 之外的 Agent。
- **候选改法**：S 内字段的一组具体取值，是可修复性的见证。

例如 A 缺木头制造木镐，B 有木头且原计划自行制造。如果目标是 A 本步制造成功，仅把 B 改为向 A 分享木头，可能已经足够。编辑范围可以只有 B，证据仍需包含 A 的材料需求与附近工作台。不能默认把报错 Agent、所有相关 Agent 都列入实际编辑范围。

范围外的计划字段保持不变。分享满足前提后，范围外原本暂缓的操作可以按共同执行规则恢复；这种执行状态变化需要记录，但不算对其计划字段的编辑。

## 3. 先明确要修复成什么

每个待处理问题建立 RepairTarget，记录目标 Agent、目标事件、依据和时域。

首批采用两类可验证事件：

1. `Make(agent, tool)`：该 Agent 的制造操作在本步实际满足配方与设施条件，产生相应制造效果。
2. `Collect(agent, material)`：目标材料已被观察到且位于面前，本步采集操作实际产生对应采集效果。

目标事件在搜索前固定。把制造改成等待、换成无关目标，或仅通过分享获得同名物品，都不能冒充制造完成。集合中存在有效进展，也不能替代指定目标事件。

缺少确定目标、相关事实缺失或超出模型时域时，保留未知依据。不能通过任意填写未知库存、设施或位置生成可行见证。

## 4. 生成候选范围和允许的改法

1. 从目标配方或工具要求提取物品、数量、目标 Agent 和设施依据。诊断附上结构化依据，生成器直接使用字段，不解析自然语言 message。
2. 关联当前持有者、已有分享承诺和目标执行者，生成有因果作用的字段修改域。
3. 允许值包括保留原操作、分享相关物品、执行目标制造或采集、为联合修复暂缓冲突操作。每个允许组合都必须符合当前动作 schema。
4. 枚举至多 K 个可编辑 Agent 的组合及其有限字段取值。6 个可编辑 Agent、K=2 时有 21 个非空 Agent 范围；另保留不修改的参照。
5. 所有目标的编辑域在同一快照内联合处理。`related_agents` 用于建立依据和排序，不直接作为已经可修复的范围。
6. 从成功见证提取真正发生变化的 Agent 和字段，合并重复结果。同等目标覆盖下，移除只增加编辑字段或 Agent 的冗余范围。

首版小团队采用有限枚举，先得到可核对的准确参照，再根据耗时决定是否需要求解器或剪枝。允许修改的有限域必须明确列出；仅搜索了更小的启发式子集时，找不到改法不能等同于该权限域内无解。

## 5. 联合验证可修复性

现有 `diagnose()` 提供前置条件检查。范围验证还需要检查候选的共同执行效果，不能只把“没有 violated”当成修复成功。

对每个候选使用独立的观测副本：

1. 替换 S 内获准字段，保留其余计划。
2. 按实际 Agent 顺序处理分享，每次转移 1 件物品；分享发生在环境动作之前，没有距离条件。
3. 重新计算共同执行保护。仍缺少已确认前提的操作暂缓；前提已满足的操作允许恢复。不能把原来的 blocked 标志永久冻结。
4. 按环境执行顺序检查已覆盖的制造、采集与资源变化，读取 `crafter/data.yaml` 的实际规则。
5. 判断目标事件是否发生，并确认没有因候选改法破坏范围外已验证可执行工作的必要条件。
6. 对同一份联合改法统计覆盖目标，检查共享库存和互相依赖。两个分别可行的修复，合并后必须重新验证。

验证器使用提交的观测、库存与计划，不读取额外模拟器状态，也不改变真实环境。只在未建模的动作或变化可能影响本次依据时，将相关候选标成未知；无关 Agent 的活动不应使所有候选一起变成未知。

| 结果 | 含义 |
| --- | --- |
| `repairable` | 找到满足权限、目标事件和共同约束的具体见证 |
| `infeasible` | 已穷尽该范围声明的有限域，仍没有见证 |
| `unknown` | 相关事实缺失、执行效果未覆盖，或搜索未完成 |

这些结论只针对声明的模型、修改域和一步时域。`infeasible` 不表示真实任务永远无解；只有另有更大范围的见证时，才可进一步归因为当前编辑容量不足。

## 6. 选择推荐范围

只从 `repairable` 候选中选择。第一版使用透明的字典序：

1. 在容量 K 内，优先覆盖更多已确认的当前执行问题；同等情况下再比较可验证的直接采集进展。
2. 覆盖相同时，优先修改更少 Agent。
3. 再优先修改更少字段。
4. 最后使用固定顺序打破平局，便于复现。

覆盖数必须来自同一个联合见证。选择器不把多个候选的独立覆盖直接相加。没有可修复候选时，返回空推荐及原因，继续现有暂缓或导航策略。

K 表示可编辑 Agent 数。证据涉及 Agent 数另行记录；人审请求次数和真实阅读时间在后续人工接口阶段计量，不能用编辑范围大小直接宣称节省了人工时间。

## 7. 与当前代码衔接

建议新增 `memory_system/repair_scopes.py`，保留现有 AgentScope Agent 和调度结构。

| 内容 | 最小职责 |
| --- | --- |
| `RepairTarget` | 固定目标事件、Agent、时域及事实依据 |
| `ScopeCandidate` | 编辑字段、具体改法、检查结果、覆盖目标与证据 |
| `generate_scope_candidates()` | 从约束和有限修改域产生候选 |
| `verify_joint_repair()` | 在观测副本中验证联合效果 |
| `select_repair_scope()` | 按容量和固定排序返回推荐或空结果 |

接线顺序：

```text
原有规划 → 最多两轮定向重规划 → 剩余诊断
    → 建立修复目标 → 生成范围和改法 → 联合验证 → 选择并记录建议
    → 继续现有执行流程
```

在现有 `coordination.jsonl` 中记录输入计划、目标、允许域、候选状态、见证、覆盖目标、编辑与证据范围、最终选择和搜索耗时。生成候选不计作已执行修改，也不写成执行经验。

本阶段采用本地枚举，不追加模型调用。人工请求界面和计划实际提交在后续阶段接入。

如果枚举已经生成可直接执行的修复，后续强自动基线必须能够使用同样候选。自动执行候选属于另一个明确实验条件；当前仍保持用户确认的定向重规划策略。仅让人确认自动生成的方案，不能作为人工额外价值的证据。

## 8. 实施顺序与验收

建议约 4–5 个工作日，按依赖推进。

| 顺序 | 核心工作 | 完成证据 |
| --- | --- | --- |
| 1 | 固定目标事件、有限修改域及输入输出 | 单独给出一个问题即可明确什么算修好、允许改什么 |
| 2 | 实现小范围生成和联合验证 | 单改、联合改、无解和未知案例均能给出依据 |
| 3 | 实现范围去重、容量约束和选择 | 推荐来自同一个有效见证，编辑范围包含实际需改的字段 |
| 4 | 接入建议输出与日志 | 两轮修复后能生成建议，原有执行策略和 30 项检查保持可用 |
| 5 | 整理自然案例及最小对照 | 能解释推荐为何足够、为何某个小范围不足，以及检查成本 |

必要案例：

- **只改提供者即可修复**：A 缺木头制造，B 分享后 A 的原制造操作成功；推荐可以只有 B。
- **需要联合改两个 Agent**：A 持木镐，B 面前是石头、原操作是 Navigator；目标为 B 本步采石。需要 A 分享工具、B 改为 do。只改一方不能完成该目标事件，K=2 时能找到见证。
- **共享资源竞争**：两个制造目标各需要 1 木头，团队只能提供 1 木头；不能把两个独立候选算成同时修好两个目标。
- **不可修复**：在当前步和声明域内，材料或工具没有来源；返回有限域内无解。
- **未知**：相关设施、库存或执行变化没有足够依据；保留未知，不能当成可修复。
- **没有进展**：全部改成 noop 不满足制造或采集目标事件。
- **保护未选计划**：候选不得消耗范围外可执行工作的必要资源，却仍宣称联合可行。

验证候选效果时，使用独立的真实 Crafter 规则执行作为参照，不能只让生成器和同一检查函数相互验证。自然失败快照与受控案例分开记录。

第一轮对照保持快照、允许域和容量相同，比较单 Agent 问题排序、完整关联集合覆盖、生成并验证可修复范围。记录范围内可修复比例、实际覆盖目标、无效推荐和检查耗时。联合验证与逐问题独立判断可作为关键消融；执行端保持共同的动作合法性保护。

本阶段建立范围生成的正确性和适用边界。实际人工增益、最终任务收益及论文新颖性仍需后续对照实验支持。

python scripts\smoke_repair_scopes.py
python scripts\evaluate_scope_examples.py --results_dir results\scope_examples_20261115
